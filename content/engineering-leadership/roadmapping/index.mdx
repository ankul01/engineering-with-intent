# Roadmapping

Effective roadmapping balances business needs, technical health, and team capacity. This guide covers creating and maintaining roadmaps that drive alignment and delivery.

## Roadmap Fundamentals

### What Makes a Good Roadmap

```
┌─────────────────────────────────────────────────────────────┐
│                   Effective Roadmap                          │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  ✅ Strategic:                                               │
│     - Tied to company/team goals                            │
│     - Shows the "why" behind work                           │
│                                                              │
│  ✅ Realistic:                                               │
│     - Accounts for capacity                                 │
│     - Includes tech debt and maintenance                    │
│                                                              │
│  ✅ Flexible:                                                │
│     - Detailed near-term, fuzzy long-term                   │
│     - Updated as priorities change                          │
│                                                              │
│  ✅ Communicative:                                           │
│     - Clear to all audiences                                │
│     - Shows dependencies and risks                          │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### Roadmap Time Horizons

```
Now           Next            Later           Future
(0-6 weeks)   (6-12 weeks)    (3-6 months)    (6-12 months)
┌───────────┬─────────────────┬───────────────┬──────────────┐
│ Committed │ High Confidence │ Planned       │ Exploratory  │
│ In sprint │ Scoped, sized   │ Directional   │ Strategic    │
│ Detailed  │ Dependencies    │ Rough scope   │ Goals only   │
│           │ identified      │               │              │
└───────────┴─────────────────┴───────────────┴──────────────┘
```

### Roadmap Components

| Component | Purpose | Update Frequency |
|-----------|---------|------------------|
| **Vision** | Where we're going (1-3 years) | Annually |
| **Themes** | Major focus areas | Quarterly |
| **Initiatives** | Key projects | Quarterly |
| **Features** | Specific deliverables | Monthly |
| **Tasks** | Implementation work | Weekly |

## Prioritization Frameworks

### RICE Scoring

```
RICE = (Reach × Impact × Confidence) / Effort

Reach:      How many users affected per quarter
Impact:     How much per user (0.25 to 3)
Confidence: How sure are we (0% to 100%)
Effort:     Person-months to implement
```

| Project | Reach | Impact | Confidence | Effort | RICE Score |
|---------|-------|--------|------------|--------|------------|
| Feature A | 10,000 | 2 | 80% | 2 | 8,000 |
| Feature B | 50,000 | 0.5 | 90% | 4 | 5,625 |
| Feature C | 5,000 | 3 | 60% | 1 | 9,000 |

### Impact vs Effort Matrix

```
              Low Effort      High Effort
           ┌───────────────┬───────────────┐
High       │   Quick Wins  │  Major        │
Impact     │   DO FIRST    │  Projects     │
           │               │  PLAN WELL    │
           ├───────────────┼───────────────┤
Low        │   Fill-ins    │  Avoid        │
Impact     │   IF TIME     │  DON'T DO     │
           │               │               │
           └───────────────┴───────────────┘
```

### MoSCoW Method

| Category | Definition | % of Scope |
|----------|------------|------------|
| **Must Have** | Critical, non-negotiable | 60% |
| **Should Have** | Important but not vital | 20% |
| **Could Have** | Nice to have | 15% |
| **Won't Have** | Out of scope for now | 5% |

### Weighted Scoring

```
Criteria (weighted):
- Business Value (40%)
- User Impact (30%)
- Technical Enablement (20%)
- Risk Reduction (10%)

Score = Σ (Criteria Score × Weight)
```

```

┌─────────────────────────────────────────────────────────────┐
│                                                              │
│  Features/Product Work         │███████████████│ 60-70%    │
│  - New capabilities            │               │            │

│                                                              │
│  Tech Debt/Maintenance         │██████│ 20-25%              │
│  - Refactoring                 │      │                     │
│  - Dependency updates          │      │                     │
│                                                              │
│  Innovation/Exploration        │███│ 10-15%                 │
│  - Prototypes                  │   │                        │
│  - Learning                    │   │                        │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### Tech Debt Prioritization

| Factor | Questions to Ask |
|--------|------------------|
| **Impact** | How much does it slow us down? |
| **Risk** | What's the cost of not fixing? |
| **Effort** | How hard is it to fix? |
| **Coupling** | Can we do it alongside other work? |

### Platform vs Product Roadmap

```
Product Roadmap:
- User-facing features
- Business capabilities
- Revenue drivers

Platform Roadmap:
- Infrastructure improvements
- Developer experience
- Scalability and reliability

Alignment:
- Platform enables product delivery
- Platform priorities informed by product needs
- Joint planning cadence
```

## Creating the Roadmap

### Planning Process

```
1. Gather Inputs (2-4 weeks before)
   ├── Business goals and OKRs
   ├── Customer feedback and requests
   ├── Technical debt assessment
   ├── Team capacity forecast
   └── Dependency mapping

2. Draft Roadmap
   ├── Map initiatives to goals
   ├── Sequence based on dependencies
   ├── Validate capacity constraints
   └── Identify risks and assumptions

3. Review and Iterate
   ├── Stakeholder feedback
   ├── Cross-team alignment
   ├── Leadership approval
   └── Communicate to team

4. Execution and Updates
   ├── Sprint planning execution
   ├── Regular progress reviews
   ├── Adjust as needed
   └── Re-plan quarterly
```

### Dependency Mapping

```
                    Feature A
                        │
            ┌───────────┼───────────┐
            ▼           ▼           ▼
        Feature B   Feature C   Platform X
            │           │           │
            └───────────┼───────────┘
                        ▼
                    Feature D (blocked until B, C, X done)
```

### Capacity Planning

```
Team Capacity per Sprint:
┌─────────────────────────────────────────────────────────────┐
│  Total: 5 engineers × 2 weeks = 10 engineer-weeks          │
│                                                              │
│  Available for new work:                                     │
│  - Minus on-call: -1 week (10%)                             │
│  - Minus meetings: -1 week (10%)                            │
│  - Minus bugs/support: -1.5 weeks (15%)                     │
│  - Minus PTO/sick: -0.5 weeks (5%)                          │
│  ────────────────────────────────────                       │
│  = 6 engineer-weeks productive capacity (60%)              │
│                                                              │
│  Split:                                                      │
│  - Features: 4 weeks (70%)                                  │
│  - Tech debt: 1.5 weeks (25%)                               │
│  - Innovation: 0.5 weeks (5%)                               │
└─────────────────────────────────────────────────────────────┘
```

### Handling Roadmap Changes

```
When priorities change:
1. Assess impact
   - What gets delayed?
   - What commitments are affected?

2. Communicate early
   - Proactive vs reactive
   - Explain the "why"

3. Reset expectations
   - New timelines
   - New dependencies

4. Document decisions
   - Why the change
   - What was traded off
```

## Common Pitfalls

### Roadmap Anti-Patterns

| Anti-Pattern | Problem | Solution |
|--------------|---------|----------|
| **Feature factory** | No strategic coherence | Tie to goals/OKRs |
| **Overcommitment** | Always behind | Realistic capacity planning |
| **No tech debt time** | Growing burden | Dedicated allocation |
| **Date-driven** | Quality suffers | Scope flexibility |
| **Set and forget** | Becomes stale | Regular updates |
| **Single view** | Misalignment | Audience-specific formats |

## Interview Quick Reference

### Common Questions

1. **"How do you create a technical roadmap?"**
   - Gather inputs (goals, feedback, debt)
   - Prioritize using frameworks (RICE, Impact/Effort)
   - Balance work types (features, debt, innovation)
   - Map dependencies and capacity
   - Communicate to stakeholders

2. **"How do you handle competing priorities?"**
   - Use objective criteria (data, impact)
   - Involve stakeholders in tradeoffs
   - Make decisions transparent
   - Accept that not everything fits

3. **"How do you balance features vs tech debt?"**
   - Dedicated allocation (20-25%)
   - Connect debt to business impact
   - Make debt visible
   - Opportunistic coupling with features

### Roadmapping Checklist

- [ ] Goals and OKRs clear?
- [ ] Inputs gathered from stakeholders?
- [ ] Prioritization framework applied?
- [ ] Capacity realistically assessed?
- [ ] Dependencies mapped?
- [ ] Tech debt included?
- [ ] Stakeholders aligned?
- [ ] Communication plan in place?
- [ ] Update cadence defined?
